# Milestone 121 — Single-video resume workflow and timing

The development app adds an off-by-default **Keep progress so this restoration can be resumed** checkbox to single-video restoration. Its stable job folder is beside the selected output and named `SwiftyTranscoder-Restoration-` plus the output filename. When enabled, an existing saved folder changes the primary action to **Resume Saved Restoration**. Cancellation/failure displays the retained folder and a Resume action; reopening the same source/output, enabling the checkbox, and preserving the same reviewed settings allows resume after restarting the app. A folder with incompatible or altered contents is refused without deletion. Finder access allows inspection of retained work. Restoration batches and previews retain their existing behavior; batch resume is not exposed by this checkpoint.

Free-space checks use the selected saved-job volume for resumable work. The controller performs full preflight before model preparation. Progress includes already completed blocks; measured remaining time uses only newly observed progress. Completion reports verified reused frames, this run's elapsed time, and average speed based only on newly restored frames. If every block was already saved, it reports elapsed time and reuse without inventing an inference speed. The cancelled monitor cannot overwrite a terminal result after awaiting saved-frame information.

The optimized app is `.build/Milestone121DerivedData/Build/Products/Release/SwiftyTranscoder.app`. It still carries development version 1.4.0 (14); the installed app, CLI launcher, and existing release artifacts were not replaced. Build, strict signature, bundled helper/model/license/capability checks passed. The complete suite passed 165 tests in 40 suites, and final focused controller tests cover no reuse, partial reuse, and all-frame reuse, along with pipeline/locking/refusal/ETA tests (29 tests in 7 suites).

Real final-build test evidence is in `.build/milestone121-evidence/` and the verification script in `.build/milestone120-evidence/verify-final-resume.py`. Short resumed outputs are provided for user playback; GUI appearance and hands-on Cancel/Resume remain user acceptance steps. Release packaging follows that acceptance, rather than presenting the development build as an accepted release.

Final real checks passed for Ctrl-C, SIGKILL after one recorded block, and SIGKILL after both blocks. Each resumed file independently inspected as 240 HEVC frames at 1920×1080 and 24000/1001, with AC-3 and AAC audio. Recorded first-block bytes and modification time stayed unchanged; completed workspaces were removed; the source hash remained unchanged. Changed-gain actual/dry-run resume and fresh folder reuse were refused. Concurrent runs were refused while the job was active. The all-blocks run reused all 240 frames and reported elapsed time without an average inference speed. Existing ordinary MKV/MP4 CLI smoke checks, elementary-video-stream equality for MP4 copy mode, and cancellation passed against the final development app. Evidence: `real-resume.log`, `*-inspection.json`, `*-resume.log`, `ordinary-cli-regression.log`, and `app-verification.log` in `.build/milestone121-evidence/`.

The user confirmed both resumed playback and the saved-progress interface, then authorized release packaging. These user acceptance checkpoints are complete.
